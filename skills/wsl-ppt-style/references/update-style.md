# 更新风格

仅在用户要求“记住/学习这次风格”“更新这个技能”或类似明确意图时维护规则。正常做 PPT 时只读取；“把这页框缩小”首先是对当前作品的修改。

## 更新步骤

1. 明确目标是本技能。阅读当前相关规则，检查用户要求是新偏好、已有偏好的修正，还是场景限定。
2. 若范围能从反馈明确判断，直接更新；只有会影响以后其他场景且无法判断时才简短确认。未确定的局部调整不升级为通用规则。
3. 修改最相关的已有条目，避免重复。视觉规则写入 `layouts.md`，讲解规则写入 `teaching.md`；仅核心决策需要同步修改 `SKILL.md`。
4. 在 `evidence.md` 记录日期、适用场景、直接要求或观察、被替代的旧规则。只保留影响风格判断的信息，不复制整段研究内容。
5. 若本地技能是链接，修改其真实目标目录，使本地和仓库保持一份来源。不要覆盖用户同时修改的无关文件。
6. 在仓库 `CHANGELOG.md` 记录变更并同步版本。用当前可用的技能检查器校验 frontmatter 和引用，审阅差异是否增加了不必要的绝对规则。

## GitHub 同步

用户要求同步、提交或推送时再执行。先确认目标仓库、当前分支和修改范围；有远端更新时先检查并正常合并，不强制推送，不覆盖用户的其他修改。

提交只包含技能、必要文档与工具的变化。`.local` 路径配置、完整原始 PPT、论文内容、私有实验材料和临时渲染结果不随风格更新提交。

报告哪些规则已更新，以及是否同步 GitHub。只做了本地更新时明确说明，不把本地保存描述成远端已更新。普通制稿不设置后台轮询或自动同步。
